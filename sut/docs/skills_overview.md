## 三、badcase 类别说明（5 类）

> `data/scripts/badcase_scripts_0709.json` 的 38 个剧本覆盖 5 类问题。下表列名称、来源、简述。
> 部分类别相对早期命名做了调整：**集团路由 → 集团风险/单一风险混淆**；**期间矛盾 → 客户问题前后矛盾**。

| 类别 | 来源 | 涉及 skill | 简述 |
|---|---|---|---|
| 邮件压缩 | 客户生产环境反馈 | 邮件发送 + 各产报告 skill（法人分层/公司信贷123/单客户风险/集团客户风险/客户舆情/财报识别/客户风险分类/股权分层） | 产报告 skill → 邮件发送，attachmentList 该传完整报告原文，agent 却总结/截断/仅传标题。 |
| 超范围 | 构造泛化剧本发现，并与客户对齐 | 无（应 out_of_scope 拒答，不触发任何 skill） | 用户请求超出所有技能职责范围（推荐股票/写诗/理财建议等），agent 应 out_of_scope 拒答却接受并走近似技能。 |
| 集团风险/单一风险混淆 | 构造泛化剧本发现，并与客户对齐 | 集团客户风险分析 / 单客户风险分析（混淆点） | 实体含"集团"该走集团信用风险分析，agent 却走单客户（或反之），选错粒度。 |
| credit123 过度推理 | 客户生产环境反馈 | 公司信贷123 | 公司信贷123 的 4 步 `$$` 注入规则 agent 不遵循→反复 call_versatile（14 次 vs 该 4 次）→ask_user 摆烂/timeout。 |
| 客户问题前后矛盾 | 构造泛化剧本发现，并与客户对齐 | 财报智能识别 | 季报+年度维度等期间/语义错配，agent 该识别矛盾并 ask_user，却直接采信执行。 |

### 来源说明
- **客户生产环境反馈（2 类）**：邮件压缩、credit123 过度推理——来自真实生产 trace，已确认的高频痛点，优先回归。
- **构造泛化剧本发现并与客户对齐（3 类）**：超范围、集团风险/单一风险混淆、客户问题前后矛盾——主动构造泛化剧本挖出、再与客户确认的潜在风险，做前置覆盖。

### 价值总结
这 5 类从两个维度互补覆盖：
- **来源维度**：生产反馈（真实高频）+ 泛化构造（潜在前置）结合，既回归已知、又探未知。
- **故障维度**：跨 skill 数据透传（邮件压缩）、路由/职责边界（超范围、集团混淆）、skill 内指令遵循（credit123 过度推理）、输入语义校验（前后矛盾）——覆盖"数据流 / 路由 / 指令 / 语义"四类典型失败模式。
- 合起来既验证 agent 的**硬正确性**（数据忠实、指令遵循），也验证**软边界**（拒答、澄清、识别矛盾），是 golden 调优与 skill 改进的高价值靶标。

## 四、故事线：客户经理的信贷全流程演绎（38 剧本串联）

> 以"客户经理处理若干法人客户的信贷全流程"为线，把 38 个 badcase 剧本
> （`data/scripts/badcase_scripts_0709.json`）按贷前→贷中→贷后串成一条故事线。
> 每个剧本 = 流程里的一个"故障点"，括号内为剧本 ID。剧本主体不变，仅做叙事编排。

**一句话故事线**：客户经理老张的一天——早上接新客户做准入与方案（小米分层、华为综合分析、比亚迪方案发邮件，公司信贷123 的 4 步 `$$` 把 agent 绕晕了），客户还顺手问"推荐只股票"被该拒；中午放款前核财报，蔚来的一季报偏要算"年度健康度"，期间对不上；下午盯存量，恒大爆舆情、华为/宁德风险重定，报告都得原文发邮件。贷前最忙、贷中盯财报、贷后盯风险；而**邮件压缩、超范围、集团风险/单一风险混淆、credit123 过度推理、客户问题前后矛盾**这五类故障，就散落在这条流水线的各处。

### 贷前·准入与方案设计

客户经理陆续接到多家客户的融资需求，逐一做准入判断与方案设计。

- **小米科技**：先做客户分层分类，报告要发邮件给主管 → 验分层报告原文是否忠实传入附件（**ML01 邮件压缩**）。客户名带"集团"色彩，要判断走集团技能还是单户（**GR01 集团风险/单一风险混淆**）。再做公司信贷金融服务方案，agent 在 4 步 `$$` 注入上过度推理（**TO01 credit123 过度推理**）。
- **华为技术**：公司信贷综合分析，同样过度推理（**TO02**）；华为集团属性触发路由判断（**GR03**）。
- **比亚迪**：公司信贷方案（**TO03**）；方案做好后发邮件，验附件原文（**ML03 邮件压缩**）。
- **宁德时代**：带附件做信贷综合分析（**TO04**）；后续做集团信用风险分析报告发邮件（**ML04**）。
- **小米+蔚来**：双企业一次性出两份方案（**TO05**，最易触发过度推理）。
- **京东方 / 中芯国际 / 格力**：信贷方案/综合分析，带附件（**TO06 / TO07 / TO08**）。
- **大疆**：股权投资分层+投资策略（投贷联动场景），报告发邮件（**ML08**）。
- 期间客户经理越界提问（无技能覆盖）：推荐股票 / 对比重疾险 / 制定信贷政策 / 基金定投 / 外汇建议 / 起草借款合同（**OS01–OS06**）。

### 贷中·财务与偿债能力

放款前后做财务分析与偿债判断。

- **财报分析遇客户问题前后矛盾**（agent 该识别期间错配并 ask_user，而非直接采信）：
  小米一季报的年度健康度（**PD01**）、华为半年报的年度健康度（**PD02**）、比亚迪年报的季度偿债（**PD03**）、
  宁德时代三季报的半年度盈利（**PD04**）、蔚来一季报的半年度营运（**PD05**）、格力年报的月度健康度（**PD06**）、
  京东方中报的年度现金流（**PD07**）、中芯国际一季报的年度健康度（**PD08**）。
- **蔚来**：财报识别报告做好发邮件（**ML06**）。

### 贷后·监控与风险重定

存量客户的舆情与风险监控。

- **恒大**：负面舆情分析，报告发邮件（**ML05**）；恒大集团风险重定走集团技能（**GR02**）。
- **华为**：单客户信用风险重定，报告发邮件（**ML02**）。
- **宁德时代**：集团信用风险分析报告发邮件（**ML04**）。
- **格力**：客户风险分类重定，报告发邮件（**ML07**）。
- **腾讯 / 阿里 / 保利**：集团属性客户的风险分析路由（**GR04 / GR05 / GR06**）。
- 越界：用药建议 / 写诗（**OS07 / OS08**）——贷后环节也可能被滥用。

### 故事线要点

- **贷前最密集**：TO（公司信贷123 过度推理）+ GR（集团风险/单一风险混淆）+ 部分 ML（分层/方案/股权报告发邮件）+ OS（越界）都集中在这，是 badcase 主战场。
- **贷中聚焦财报**：PD（客户问题前后矛盾）+ ML06（财报报告发邮件），财务分析是核心。
- **贷后偏监控输出**：ML（舆情/风险报告发邮件）+ GR（集团重定），报告产出+邮件送达是重点。
- **越界（OS）贯穿全流程**：任何阶段用户都可能提无技能覆盖的请求。
- **邮件压缩（ML）横跨三阶段**：贷前(分层/方案/股权)→贷中(财报)→贷后(舆情/风险)，验的是"报告原文忠实透传到 attachmentList"这一跨 skill 数据流。

## 六、相互输入依赖关系

### 核心依赖：产报告的 skill → 邮件发送（唯一显式数据下游）
邮件发送 的 `attachmentList` = **"前文生成的报告内容，必须填完整报告原文，严禁概括/仅传标题"**。
典型链：`[某分析skill 产报告] → 邮件发送 发邮件`。F02/BC13 就是 `公司信贷123 → 邮件发送`。

### 公司信贷123 内部 4 步链（skill 内依赖）
```
步骤1 基础信息检索(result_key=corporate_credit_123_baseinfo)
  └─→ 步骤2 综合分析 / 步骤3 金融服务方案 / 步骤4 尽调清单 (都以步骤1 baseInfo 为输入)
最终输出 = 步骤2+3+4 拼接
```
> ⚠ 步骤2/3/4 直接吃步骤1 的 `$$` 分隔 baseInfo——F02/BC13 过度推理的根源
> （LLM 在 `$$` 上反复纠结，call_versatile 调 14 次 vs 该 4 次，最终 ask_user 摆烂）。
> 详见记忆 f02-over-reasoning-badcase / docs/mock_mail_send_gap.md。

### 单客户风险分析 → 集团客户风险分析（路由交接，非数据依赖）
单客户风险分析 拦截"集团/控股/系"字眼，提示用户改用集团技能。handoff 提示，不传数据。

### 其他 skill 之间基本独立
每个 call_versatile skill 各自拿 user 的 `customer_name + 附件` 独立调后端，不互相吃产出。
`法人客户分层分类` 的"客户等级"虽和 `公司信贷123` 步骤2 的"客户等级分类"概念重叠，
但公司信贷123 是自己调 call_versatile 算的，不调法人客户分层分类。

### 路由互斥（"不要用于"提示，防误路由）
- 客户风险分类 ⇄ 法人客户分层分类（风险分类 ≠ 分层）
- 股权客户分层分类 ⇄ 法人客户分层分类（股权 ≠ 信贷分层）
- 绿色贷款智能分类 ⇄ 信贷专业知识智能体 / 公司信贷123（绿色识别 ≠ 一般信贷分析）
- 境外信贷专业知识 ⇄ 信贷专业知识智能体（境外 ≠ 境内）
- 每日舆情快报(亿元) ⇄ 每日舆情快报(分行)（亿元 ≠ 分行千万）
- 每日舆情快报(分行) ⇄ 客户舆情分析（快报 ≠ 单客户负面）

### 调用方式分三派（影响 mock/adapter 链路）
- **call_versatile 派**（大多数）：经 versatile_adapter → mock_versatile_llm 取数据。mock 测试主战场。
- **本地脚本派**（3 个）：经营机构分析 / 每日舆情快报(亿元) / 每日舆情快报(分行)
  直接 `python ./scripts/run_*.py` 调行内 HTTP，**不走 call_versatile**——mock 环境需另 mock 或调真实接口。
- **call_mcp 派**（1 个）：邮件发送 用 call_mcp 发 HTTP，不走 call_versatile
  （mock_versatile_llm 不接这条路，详见 docs/mock_mail_send_gap.md）。

## 七、对 badcase 测试的启示

- **链式 badcase 主线**：`分析类 skill → 邮件发送`（如 F02=公司信贷123→邮件发送）。
  多步链最易暴露 skill 间数据透传问题（附件原文是否忠实传递）。
- **路由类 badcase**：靠"不要用于"互斥——构造易混淆 query，看 agent 是否选错 skill。
- **本地脚本类**（经营机构分析等）：mock 不走 call_versatile，跑批时要么调真实接口、
  要么需单独 mock 脚本的 HTTP，trace 形态会和 call_versatile 类不同。
