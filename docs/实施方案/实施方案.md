## 1. 选型结论

**数据集：τ-bench**（零售 retail 场景为主）

理由：
- 自带约 15 个工具 API + 政策手册（policy doc）→ skill 不用造，且政策手册是 GU 的天然真值；
- 多步工具调用、任务开放（无唯一正确路径）→ 软标工具有用武之地；
- 任务成败有数据库终态硬校验 → golden 标注可对拍的锚点；
- 环境相对轻（相比 AppWorld/WorkArena）；
- 官方 harness 自带 baseline agent + LLM 用户模拟 + 判分接线，agent 层零搭建。

**模型：DeepSeek API**（OpenAI 兼容，直接接入 τ-bench harness）。强档/弱档具体型号与 key 来源待定（开工前拍板）。

备选：HotpotQA（数据本地已有，省环境工作，但无 skill 体系、硬答案任务，检验力弱，仅作降级方案）。

## 2. 总体流程（一期）

```
τ-bench 环境搭建（官方 harness + DeepSeek 端点）
   ↓ 跑批（强/弱两档 × num_trials 多次采样）
原始轨迹 + 成败硬判分（τ-bench reward）
   ↓ adapter（自研，本项目核心工作量）
messages 格式 trace 目录 + skills_flat/*.md + 剧本Q
   ↓
golden_gen  →  golden_output.jsonl + global_understanding/
   ↓                                        ↘ 对拍①：result vs 硬判分
coldstart_mining  →  final_rules.json      对拍②：GU vs 政策手册
   ↓                                        对拍③：expected_behavior 抽样人工
fault_localization  →  golden_localized.jsonl
   ↓
对拍④：注入故障案例的归因命中率
```

## 3. 工作分解

### 阶段 0：环境与基线（约 0.5 天）
- 装 τ-bench（pip 包或源码），跑通官方示例 agent，接通 DeepSeek 端点；
- 确认 intranet_bundle 可运行：`python run.py golden --help`、mock 模式冒烟；
- 明确 LLM API key 配置方式（`LLM_API_KEY` env / config.yaml）。

### 阶段 1：skill 与剧本适配（约 0.5 天）
- 把 retail 场景 15 个 API 各包一个 `skills_flat/<api_name>.md`：名称、用途、参数、约束（从政策手册摘录相关条款）——模仿 bundle 内现有 skill 写法；
- 任务直接作为剧本 Q；如需触发 golden_gen 的 progressive 分组模式（>30 skill），把 API 按参数级用法拆细（可选，二期做）。

### 阶段 2：跑批产 trace（约 0.5~1 天）

**核心原则（v3 修订）：被测 agent 全程同一配置（同模型 + 完整手册 + 完整 skills），好坏 case 不允许来自不同配置的 agent**——否则工具评估会混入模型能力差异的噪声。批次分两类：

- **baseline 批次**：基线模型 + 完整政策手册，自然好坏混合。模型选型目标 = 通过率居中（40%~70%，好坏都够）；GLM5.1 实测 10/10 过强，候选 qwen-turbo/qwen-plus，先试跑定基线。用户模拟器固定用 GLM5.1（用户侧质量不作为自变量）。
- **inject 批次**：同一基线模型 + 故障注入（wiki 条款删节 / 工具实现 patch 脏数据 / skill 文档改坏），稳定复现同根因 badcase，真值记入 `eval/injection_manifest.json`。

**放量**：每任务 `num_trials` 跑 3~5 次（温度采样使轨迹分化），把 badcase 总量放大到数百条，满足 coldstart 分组聚合（≥2 条成组）的体量需求。
记录：完整 messages（含 tool_calls）、每次 trial 的 τ-bench reward。

（废弃的 v2 设计：强档产 goodcase / 弱档产 badcase 双轨——因破坏"同一被测 agent"前提而废；`run_batch.py --tier` 保留但仅 baseline/inject 两种用途。）

### 阶段 3：adapter（本项目核心，约 1 天）
写 `adapter/tau2bundle.py`，把 τ-bench 轨迹转成 bundle 的 messages-only 格式：
- 顶层 `{script_id, conversation_id, script, messages[], errors}`；
- messages 逐条 `{_class, role, content, metadata, tool_calls[{_class:"ToolCall", id, type:"function", name, arguments}]}`；
- 参照样例：`intranet_bundle/runs/agent/20260804_155219/traces/trace_BC001.json`；
- 输出到 `runs/<ts>_<档>/traces/`，并在同批目录落 `tau_reward.json`（conversation_id → 硬判分）供对拍。

### 阶段 4：golden_gen 实测 + 评价（约 0.5 天）
- `python run.py golden --trace-dir runs/<ts>/traces --regenerate-global`；
- 评价口径详见 **《评估方法.md》§一**（三层）：
  - L1 硬锚点对拍：result vs τ-bench reward 一致率，分歧逐条归因；
  - L2 EB 三要素一致性：移植 openjiuwen `eval_golden_accuracy.py`，标准 EB 由任务 expected actions 半自动构造，LLM 裁判（2/1/0 + 超集容忍）+ embedding 伴随；
  - L3 人工评审：`golden_review_ui` 抽 30~50 条（先跑 trace_md），校准裁判可信度；
  - GU 对拍政策手册条款清单（覆盖率 + 幻觉条款数）。

### 阶段 5：coldstart + fault_localization 实测（约 1 天）
- `python run.py coldstart --trace-dir ... --golden golden_output.jsonl --skills skills_flat` ——首次端到端跑通，记录所有报错与修复；
- `python run.py localize --golden ... --rules final_rules.json --trace-dir ...`；
- 归因评估见阶段 6。

### 阶段 6：故障注入与归因评估（约 0.5~1 天）
真值自己造，三类注入（同时承担"错误模式集中"的构造职责）：
1. **改坏 skill**：挑 2~3 个 skill .md 删掉关键约束（如退货时限），重跑一批任务 → 成片同根因 badcase，真值=被改的 skill；
2. **API 脏数据**：patch 某 API 对特定输入返回错误结果 → 真值=该 API 对应 skill；
3. **弱模型自然失败**：失败模式自然聚集于头部政策违例（忘核验身份、改单当取消、编造政策等），真值=政策违例条款（半自动映射）+ 人工标注 20~30 条兜底。

评价口径详见 **《评估方法.md》§二**：`eval/injection_manifest.json` 真值台账；fault_localization top1/top3 命中率（分规则反查/LLM 兜底两层统计）；coldstart `skill_attribution.top3` 同口径 + 簇混淆检查；规则人工抽评；规则效用前置验证（judge+诊断规则 vs 裸 judge 对 reward 的一致率，作二期闸门依据）。

### 阶段 7：一期报告（约 0.5 天）
- 每个工具：跑通情况、对拍指标、典型失败案例、修复/改进建议；
- 输出 `测试报告.md` + 全部中间产物归档；
- **一期→二期闸门**：规则挖掘质量达标（归因命中率、人工抽评通过）才启动二期，否则先修工具。

## 4. 二期：优化 A/B（验证 DAG 工具的端到端价值）

- 对照设计：同一批任务、同一 SkillOpt 优化器（源码见 `D:\expected_behavior-理论基础分析2\SkillOpt\`），
  - A 组：裸评估器（τ-bench reward 或基础 LLM judge）驱动优化；
  - B 组：评估器注入 coldstart 产出 `final_rules_diagnostic.txt`（`{diagnostic_rules}` 槽位）后驱动优化；
- 指标：优化前后 τ-bench pass rate 提升幅度、收敛轮数、规则增强是否带来更稳的提升；
- 注意：这是**间接证据**（confound 多），结论必须与对拍④的直接度量互参；
- 详细方案在一期报告后另行细化。

## 6. 风险与降级

- **τ-bench 环境装不上**（依赖/网络）→ 降级 HotpotQA + 自建 4~6 个 wiki 工具 skill，检验力打折但链路仍可测；
- **bundle 工具对 trace 格式有隐性假设**（如必须出现某类消息）→ adapter 阶段先用 1 条 trace 走通 golden_gen mock 冒烟再跑批；
- **coldstart 首次实战报错多** → 允许修 bug，但所有改动记录进报告（这本身是测试成果）；
- **API 成本**：两档 × num_trials 跑批 + 三个工具的 LLM 调用，先用 10 条小规模全流程试跑确认成本再上量。
