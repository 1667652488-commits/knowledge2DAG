# 评估方法（golden 工具 & dag 工具）

> 本文档是《实施方案.md》阶段 4~6 的具体化：两个被测工具各自的评价口径、指标、数据来源与产出物。
> 方法论主要借鉴 `D:\openjiuwen_agentsolution0814\test\eval_golden_accuracy.py`（EB 一致性评测）与
> `D:\openjiuwen_agentsolution0814\test\trace_attribution\`（归因真值集验证范式）。

## 〇、红线：评估资产与被测工具严格隔离（防泄题）

- **被测工具只准读**：`runs/<批次>/traces/`（轨迹原文，adapter 已保证不含 reward）+ `data/skills_flat/*.md`；
- **评估侧资产（被测工具禁读）**：`eval/dataset_v2.json`、`tau_reward.json`、`eval/task_reference.jsonl`、`eval/injection_manifest.json`、政策手册 wiki 完整版；
- 违反此原则 = 给工具泄题，测出的指标无效。改代码时如涉及工具输入，先核对本条。

## 一、golden 工具（软标生成）的评价

### 三层口径（成本从低到高，互补）

**L1 硬锚点对拍（自动，全量）**
- golden 产出 `result`（通过/部分通过/失败）vs τ-bench reward（DB 终态硬校验，1/0）。
- 指标：一致率（通过↔reward=1、失败↔reward=0；"部分通过"单列统计其 reward 分布）。
- 分歧 case 逐条归因：软标错 / 硬判分盲区 / 轨迹质量问题。
- 数据：`runs/<ts>_<档>/tau_reward.json` × `sut/runs/golden/<ts>/golden_output.jsonl`。

**L2 EB 一致性（LLM 裁判 + embedding 伴随，借鉴 eval_golden_accuracy.py 的裁判口径）**
- **参考真值（零人工构造）**：直接用 τ-bench 任务自带的 expected actions（判分依据的工具调用序列）+ instruction，由脚本机械渲染成裁判参考文本（`eval/task_reference.jsonl`）。**不做"expected actions → 标准 EB"的人工翻译层**——裁判模型直接判"EB 核心含义 vs expected actions"是否一致，格式不同不影响语义判定。
- **配对**：按 script_id（= `tau_<task_id>`）取交集。
- **裁判口径**（沿用 openjiuwen，逐要素 2/1/0）：
  - scenario（场景前提）←→ 任务 instruction；
  - should（应该做）←→ expected actions（EB 是否正确覆盖该任务应有的行为）；
  - should_not（不应该做）←→ expected actions 中无真值，改为对照**该任务相关政策条款**（政策手册为唯一权威来源）判定；
  - 每要素：等价(2) 行为方向+关键约束一致 / 部分(1) 方向对但缺一要素或陷入实现层细节 / 不等(0) 方向相反/遗漏关键工具/关键约束冲突；整条综合：全2→2，有1无0→1，任一0→0；
  - **超集容忍（tolerant）**：候选是合理超集/措辞粒度不同/合理细化且无要素 0 → 视同严格等价。
- **头版 4 指标**：[LLM]严格(含容忍) / [LLM]宽松(三要素均≥1) / [相似度]整条 sim≥0.75 / [相似度]平均整条 sim。附三档分布、三要素等价率、分组准确率、不一致 case 清单。
- **实现**：移植 `eval_golden_accuracy.py` → `eval/eval_golden_accuracy.py`（原脚本仅依赖 httpx + 裁判/embedding 配置；裁判/embedding 配置走 `eval/eval_judge_config.json`，不入库），裁判 prompt 的"标准答案 EB"位替换为 task_reference 文本。

**L3 人工评审（抽样，校准裁判可信度）**
- 工具：`sut/golden_review_ui/app.py`（现成，左 trace md + 原始 golden，右人工接受/修改，产 `golden_review.jsonl`）。
- 前置：需先跑 sut 的 `trace_md` 把本批轨迹渲染为 `runs/<RUN>/md/trace_<id>.md`。
- 规模：抽 30~50 条；指标 = LLM 原始 EB 直接接受率（accepted 占比）+ result 修改率；同时用人工结论校准 L2 裁判的严格度。

**GU（全局理解）对拍政策手册（半自动）**
- 政策手册（81 行）人工拆成条款清单 `eval/policy_clauses.json`；
- LLM 初判 GU 对每条款的覆盖（覆盖/未覆盖/幻觉条款），人工复核争议项；
- 指标：条款覆盖率、幻觉条款数。

## 二、dag 工具（coldstart 挖掘 + fault_localization 归因）的评价

### 范式：真值集显性化（借鉴 trace_attribution 的 attribution_scripts.json）

**`eval/injection_manifest.json`** —— 所有故障注入的台账，评估脚本直接读它算分，不靠人记：

```json
{
  "injections": [
    {
      "batch": "20260821_103000_inject_return_policy",
      "type": "skill_doc_corrupt",
      "target_skill": "return_delivered_order_items",
      "change": "删除强约束：退货仅限 delivered 状态订单",
      "affected_tasks": "所有涉及退货的任务",
      "expected_attribution": ["return_delivered_order_items"]
    }
  ]
}
```

### 三类真值来源

1. **改坏 skill**（skill_doc_corrupt）：删/改 skill .md 关键约束 → 真值=被改的 skill；
2. **API 脏数据**（api_dirty_data）：patch 某 API 特定输入返回错误结果 → 真值=该 API 对应 skill；
3. **弱模型自然失败**（natural_failure）：真值=政策违例条款（半自动映射）+ 人工标注 20~30 条兜底。

### 主评估：基础评估器 ± DAG 规则（v3 修订，评估 DAG 工具的核心设计）

检验 DAG 工具的设计主张"规则赋能外部评估器"。同一批轨迹（baseline + inject 批次混合），两组对照：

- **A 组：基础评估器**（`eval/base_judge.py`，简单 LLM judge）：输入 trace，输出 `{is_badcase, fault_skill, reason}`；
- **B 组：基础评估器 + DAG 规则**：同评估器，system prompt 注入 coldstart 产出 `final_rules_diagnostic.txt`（`{diagnostic_rules}` 槽位），同样输出。

真值：is_badcase ← τ-bench reward（1=goodcase，0=badcase）；fault_skill ← `injection_manifest.json` 的 expected_attribution。

三维对比指标：

| 维度 | 口径 |
|---|---|
| 准确率 | badcase 检出率（vs reward）；fault_skill top1 命中率（vs manifest）——B 组应显著高于 A 组 |
| 速度 | 每条评估的端到端耗时（规则前置知识应减少评估器的推理探索） |
| token 消耗 | 每条评估的 input+output token（规则 vs 规则带来的 prompt 增量，看净效应） |

### 次评估：fault_localization 自身归因质量

- `attributed_to` top1 / top3 命中率（对照 manifest 的 expected_attribution）；`source` 分层统计——规则反查（matched_rules）命中多少、LLM 兜底命中多少，各自准确率（定位规则层弱还是兜底层弱）；
- coldstart `skill_attribution.top3` 同口径命中率；不同注入簇之间是否被错误归并（簇混淆率）；
- 规则人工评审（抽样）：`final_rules_natural_language.txt` 抽 20~30 条，三维度打分——规则正确性（对照政策手册）/ supporting_trajectories 是否真支持 / 归因 skill 是否合理。

### 正确 SOP 侧：降级为弱评估（v3 修订）

错误模式评估有注入真值（skill + 错误类型对上即命中），是硬指标；正确 SOP 没有等价真值（"归纳得好不好"是模糊判断）。处理原则：

- **不设硬指标**，只做两项：
  1. **幻觉检查**（半自动）：归纳出的正确 SOP 是否幻觉出政策手册没有的规则——SOP 质量最要命的缺陷，可判；
  2. **描述性人工记录**：覆盖度、可用性等软维度，抽样描述，不计分。
- **DAG 工具验收主指标 = 错误模式准确率 + 归因命中率**（有真值的部分）。
- 注意输入约束：coldstart 的"缺失检查点"检测用正确链路当参照系，故输入数据保留约 30% goodcase 作参照（不为学习正确做法——τ-bench 的政策手册 + expected actions 已是权威正确知识来源）。

### 规则效用前置验证

已并入上文「主评估：基础评估器 ± DAG 规则」——同一对照设计同时产出准确率与速度/token 三维指标，作为二期 SkillOpt A/B 的启动依据之一。

## 三、产物归放

```
eval\
  eval_golden_accuracy.py     ← 移植自 openjiuwen（L2 裁判）
  eval_judge_config.json      ← 裁判/embedding 配置（不入库）
  task_reference.jsonl        ← 任务参考真值（instruction + expected actions 机械渲染，零人工）
  build_task_reference.py     ← 从 tasks_test.py 生成 task_reference.jsonl 的脚本
  policy_clauses.json         ← 政策手册条款清单（GU 对拍用）
  injection_manifest.json     ← 故障注入台账（归因真值）
  base_judge.py               ← 基础评估器（±DAG 规则两组，输出 is_badcase/fault_skill + 耗时/token）
  check_attribution.py        ← 归因命中率评估脚本（读 manifest + golden_localized.jsonl）
  eval_dag_rules.py           ← 主评估：A/B 组准确率/速度/token 对比
  human_review.md             ← 人工评审记录（L3 + 规则评审）
```
